## 4. 증가가 쌓인 단계

| 단계 | 생성 요청 H / V | H 입력 | V 입력 | 입력 차이 H−V | 출력 H / V |

재진술은 1요청씩이며 입력은 H 448,382 대 V 173,960, 출력은 12,898 대 20,286이다. V의 별도 기본 요약 3회는 입력 429,173·출력 62,552다. 위 단계 표에는 이 기본 요약 요청을 섞지 않았다.

확인: 8단계는 양쪽 6요청인데 입력이 H 1,434,829 대 V 687,204였다. 12단계도 양쪽 8요청인데 H 3,152,216 대 V 1,181,718이었다. 10단계는 H의 요청 수가 오히려 적은 6 대 10건인데도 H 입력이 837,072토큰 더 많았다. **주된 차이는 호출 횟수만으로 설명되지 않는다.**

단계와 재진술을 대응시켜 `입력 = 요청 수 × 요청당 평균 입력`으로 산술 분해했다. 각 단계의 평균을 대칭 가중해 다음 항등식을 사용했다.

```text
H 입력 − V 입력
 = (H 요청 수 + V 요청 수)/2 × (H 평균 입력 − V 평균 입력)
 + (H 평균 입력 + V 평균 입력)/2 × (H 요청 수 − V 요청 수)
```

- 대응한 단계·재진술의 입력 차이: 10,536,883토큰.
- 요청당 평균 입력 차이 항: 9,876,237.3토큰, **93.7%**.
- 요청 수 차이 항: 660,645.7토큰, 6.3%.
- 여기서 V만 수행한 기본 요약 입력 429,173을 빼면 전체 순차이 10,107,710과 정확히 일치한다.

이 분해는 관측값의 항등식이다. “추론 서명이 원인의 93.7%”나 “메모리 파일이 원인의 6.3%”라는 뜻이 아니다. 커진 평균 입력에는 남은 대화, 추가 작업의 출력, 서명된 추론 상태와 다른 내용이 함께 들어 있다.

출력도 같은 방향이다. 과제 단계만 보면 H 675,708 대 V 351,571로 H가 324,137토큰 더 생성했다. V는 이 외에 요약 출력 62,552토큰을 지불했는데도 전체 출력이 H보다 254,197토큰 적었다. H가 기본 요약을 생략해 아낀 비용보다 과제 중의 추가 생성·재전송 비용이 커진 표본이다.

| 3단계 뒤 | 8,564 | 58,593 | 5,928 | 30,798 |
| 6단계 뒤 | 35,796 | 108,934 | 10,513 | 38,543 |
| 9단계 뒤 | 57,855 | 150,146 | 8,769 | 35,361 |

**확인 불가:** 두 값의 범위가 같다는 증거는 없다. 다음 실제 요청에는 공통 시스템·도구 정의·새 지시문도 들어가며 V에서도 차이가 난다. 따라서 이 표만으로 post_tokens가 거짓이거나 차이 전부가 누락 추론 토큰이라고 단정하지 않는다. 또한 정확한 전체 크기로 계산했어도 60% 임계점을 넘었는지는 당시 `context.window`와 실제 판단 입력을 함께 대조해야 한다. “추정 버그가 임계 분기를 잘못 골랐다”는 인과 판정은 아직 확인 불가다.

확인한 문제는 더 좁고 명확하다. **접은 문자 수와 작은 post_tokens 표시만으로 다음 실제 요청의 총 입력과 누적 비용이 줄었다고 간주하면 이 실행을 잘못 평가한다.** 실제 다음 요청·후속 여러 요청·최대 단일 입력을 검증 지표로 함께 써야 한다.

## 6. 원인이 아닌 것과 아직 모르는 것

- 전송 재시도나 누락 복구로 이 입력 차이가 생긴 증거는 없다. H/V 생성 168건은 모두 HTTP 200·완전 응답이고 모델 사용량 합계가 기존 최종 결과와 정확히 일치한다. 계수 요청 2건도 별도 보존했다.
- Stop active의 추가 턴이 아니다. H는 shadow이고 V는 기본 조건이다. 두 조건의 과제 Stop은 12건씩 모두 completed로 판정됐고 개입은 없었다.
- 독립 Opus 판정 38건이나 Jev shadow 요청을 실행 모델 입력에 합친 수치가 아니다. 분석한 입력·출력은 지정한 Haiku 실행 캡처만의 값이다.
- 처음 요청 입력은 H 23,192 대 V 22,440, 차이 752토큰이었다. 플러그인 스키마·초기 정본 안내 같은 고정 비용은 있지만, 이것만으로 후반의 수십만 토큰 요청이나 누적 1,010만 차이를 설명할 수 없다.
- 추론 블록·정본 관리·복구·기타 도구 작업 각각의 정확한 토큰 기여량과 인과 효과는 확인 불가다. 서명을 임의로 문자/4로 환산하지 않는다. 구성 요소를 하나씩 바꾼 실험도 아직 없다.
- 한 과제·한 시드의 묶음 비교다. H의 모든 추가 출력이 필요 없는 작업이었다거나 모든 과제에서 같은 비율로 악화된다는 결론은 내리지 않는다. 다만 이 표본에서는 완료·위반·재진술 점수의 이득이 없었다.

## 7. fix-harness가 검토할 수정 우선순위

이 절은 수정 제안이며 이 보고 작업에서 제품 코드나 동결 실험을 바꾸지 않았다.

1. **부분 접기로 기본 요약을 대체해도 되는 조건을 실제 입력 예산으로 검증한다.** 텍스트 기반 추정값과 다음 실제 요청을 구분하고, 남아 있는 assistant·추론 상태까지 포함해 한도를 관리해야 한다. 서명 블록을 임의 절단하는 수정은 제안하지 않는다. 공급자·엔진이 지원하는 정리 경로와 도구 호출/결과 일관성을 함께 검증해야 한다.
2. **정본 관리의 작업량을 제한한다.** 압축 경계의 재읽기·통합과 매 단계의 PHASE/에피소드 갱신을 구분하고, 내용이 바뀌지 않는 재작성·중복 보관을 막는 검사를 둔다. 초기 Skill은 “새로 배운 것이 없으면 파일을 바꾸지 말라”고 하지만 이 표본에서는 5~12단계까지 갱신이 이어졌다. 개별 갱신의 중복 여부는 별도로 확인해야 하며 19회 쓰기를 전부 중복으로 분류하지 않는다.
3. **원문 복구가 비용을 다시 키우는 경로를 측정한다.** read_coordinate 11회, 특히 10단계의 7회 조회가 필요한 범위만 반환했는지와 이후 대화 보존량을 확인한다. 8단계의 두 조회는 실제로 offset/limit를 사용했으므로 “항상 전체 원문을 읽었다”고 일반화하지 않는다.
4. **절감 회귀 검사는 결과와 실제 전송량을 함께 본다.** 접기 문자 수뿐 아니라 동일 과제의 완료·제약 검사, 다음 요청 입력, 압축 사이 최대 입력, 누적 일반/캐시 생성/캐시 읽기 입력, 출력과 정본·복구 도구 호출을 함께 남긴다. 현재처럼 36개 결과가 접혔다는 검사만으로는 이번 총량 증가를 막을 수 없다.

수정 후 이 한 쌍을 다시 실행하더라도 그것은 버전이 바뀐 새 자료다. 원래 H/V와 이번 보고서를 덮어쓰지 않고, 원래 관측을 성공으로 바꾸지 않아야 한다. 본 보고에서 추가 실행을 승인하거나 전체 36회를 다시 시작하지 않았다.
